# 01 需求与验收门禁

门禁编号：`G1`

## 1. 目标

确认团队知道要解决什么问题、哪些内容不在范围内、如何判断完成，以及哪些假设和
风险尚未解决。需求不清楚时不得进入架构设计。

## 2. 适用范围

- 新项目、新版本或重要功能基线：执行完整 `G1`。
- 已有有效需求与验收基线：快速变更可以直接复用，不重建完整需求文档。
- 标准开发：只评审新增或变化的需求、范围和验收增量。
- 高风险变更：重开受影响范围的需求与验收，不要求复制未受影响的全部需求。
- 任务只是修复现有行为时，可引用现有需求或测试基线；若要改变行为或验收标准，
  必须先执行需求增量评审。

判定深度：

- 新项目、新版本或重大功能：建立完整需求与验收基线及追溯关系。
- 已有项目的局部变更：只检查本次影响的目标、范围、验收条件和风险，引用未受影响
  的现有基线。
- 不改变既有行为的简单任务：现有代码、测试和简短任务说明能够证明目标和验收时，
  不要求新建完整需求文档或验收追踪矩阵。

门禁处置应标记为：

- `EXECUTED`：本次执行 `G1` 并给出 `PASS / REWORK / WAIVER`。
- `REUSED`：引用仍然有效的需求基线，不生成新的通过结论。
- `NOT_TRIGGERED`：任务不改变需求或验收，且已有基线足够。

## 3. 进入条件、输入与内容标准

进入条件：

- 用户目标、问题背景和本阶段范围已经提供，或明确标记为待确认。
- 当前需求基线及其版本已知；没有基线时，确认本次需要建立完整或增量基线。
- 关键未决问题已有负责人或状态，不会在未知情况下进入架构设计。
- 修复现有行为时，已找到可引用的现有需求、验收、测试或可复现行为。

输入：

- 用户目标、问题背景和已有约束。
- 当前项目范围或版本目标。
- 已有需求、验收和测试基线及版本。

必须满足的内容与判定标准：

- 完整需求基线至少包含问题与目标、范围与非目标、每条 Must 需求的唯一 ID、可判定
  验收条件、验证方式，以及关键假设、风险和开放问题。
- 可以直接引用现有需求文档、版本规格、Issue、任务报告、测试输出、交付报告或其他
  等价证据，不规定固定文件模板。
- 局部变更只在现有需求信息、任务报告或简短任务说明中补充受影响的需求、验收、
  边界和风险，不复制未受影响内容。
- 已有基线可直接引用，不复制第二份真值。
- 需求信息只维护需求与验收条件，不记录门禁结论。`G1` 结论可以保存在任务报告、
  变更记录、commit、PR 描述或项目状态记录中，并引用 `REQ` ID 和需求版本。
- 只有正式审批、独立评审、审计或其他正式治理流程明确要求时，才建立独立正式记录。

## 4. 阻断标准

| ID | 阻断标准 | 必需证据 |
| --- | --- | --- |
| `REQ-01` | 目标描述的是可观察结果，而不是只列实现任务 | 问题、目标、成功结果 |
| `REQ-02` | 范围与非目标明确，未批准内容不会被默认为本期需求 | 范围条目或影响边界 |
| `REQ-03` | 每条适用 Must 需求都有唯一标识、可判定验收条件和验证方式 | 完整映射、受影响 ID 或现有测试 |
| `REQ-04` | 需求之间不存在未处理的直接冲突或重复定义 | 冲突处理记录或核对结果 |
| `REQ-05` | 关键假设、约束、依赖和风险有负责人或处理策略 | 风险记录或本次影响说明 |
| `REQ-06` | 需要用户决策的问题已解决，或明确不会阻止本阶段开始 | 开放问题状态 |

以下情况必须判定 `REWORK`：

- “性能更好”“体验更顺畅”等目标没有可验证口径。
- 本次适用的 Must 需求没有验收方式。
- 同一行为在不同条目中存在矛盾。
- 本次范围或影响边界缺失，导致实现过程中可以不断增加范围。
- 关键外部依赖或授权条件未知，却计划直接进入实现。

## 5. 判断说明

- 验收条件不一定必须自动化；可以人工验收，但必须写明输入、操作、预期结果和证据。
- 需求应描述外部可观察行为，避免把“使用某框架”写成用户价值。
- 无法量化的质量目标可以作为观察项，但不能代替核心交付验收。
- 用户明确接受的风险可以保留，但必须进入风险记录。
- 对已有项目，修复“当前不符合既有契约”的行为属于恢复基线，不一定产生新需求。
- 改变既有契约、新增可观察行为或调整验收标准时，不能只用“局部 Bug”标签跳过增量。

## 6. 通过条件与放行规则

- 本次执行 `G1` 时，`REQ-01` 至 `REQ-06` 全部通过：`PASS`。
- 任一阻断项失败：`REWORK`。
- 任一适用检查未执行、证据缺失，或证据未对应当前需求版本：`REWORK`。
- 只有非阻断项存在且已记录：仍可 `PASS`。
- 例外必须符合规范包总则，且不得隐藏删除的验收条件。
- 复用既有基线时记录 `REUSED` 及引用，不生成新的 `PASS`。
- 简单任务只有现有行为、代码和测试证据且判定清楚时，可以使用 `REUSED` 或
  `NOT_TRIGGERED`，不要求补建完整需求追踪矩阵。

## 7. 下游影响

需求或验收条件发生变化时，需求门禁失效。必须重新评估：

- 架构是否覆盖新增或变化的范围。
- 任务计划是否仍完整。
- 测试和验收策略是否仍能证明新行为。
