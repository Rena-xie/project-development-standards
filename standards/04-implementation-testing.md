# 04 实现与测试门禁

门禁编号：`G4`

## 1. 目标

确认实现与已批准设计一致、变更范围可控、验证与风险相称，并且交付结论只基于当前
产物状态的真实证据。实现完成不等于测试或验收完成。

## 2. 适用范围

`G4` 是任务级门禁。每个实现、修复、配置或文档交付任务都要执行与其模式相称的验证。

| 任务模式 | 上游门禁处理 | `G4` 要求 |
| --- | --- | --- |
| 快速变更 | 引用有效基线；行为或验收变化时执行 `G1` 增量 | 目标测试、静态检查、回归与 diff 检查 |
| 标准开发 | 执行受影响范围的 `G1-G3` 增量 | 按调用链和风险选择集成、契约或 E2E 验证 |
| 高风险变更 | 重开受影响的 `G1-G3`，加载安全门禁 | 扩大影响分析，必要时全量测试、迁移和恢复验证 |

`G4` 通过只代表当前任务达到实现验收，不代表版本发布。`G5` 只在形成发布候选时执行。

## 3. 前置条件

- 当前任务已经选择快速变更、标准开发或高风险变更模式，并记录判断依据。
- 快速变更引用了有效基线，或记录了最小行为与验收基线。
- 标准和高风险变更的适用上游门禁已经 `PASS`，或存在仍在批准范围内的 `WAIVER`。
- 当前任务有明确验收条件、影响范围、非范围和完成定义。
- 已读取项目配置中的测试、静态检查和构建命令。

## 4. 阻断标准

| ID | 阻断标准 | 必需证据 |
| --- | --- | --- |
| `IMP-01` | 变更可追踪到当前任务，并引用有效需求、设计或行为基线 | 变更记录与基线引用 |
| `IMP-02` | 未混入未批准的功能、重构、依赖或发布操作 | 变更范围说明 |
| `IMP-03` | 公共行为、边界、错误和副作用已按风险验证 | 测试与运行结果 |
| `IMP-04` | 适用的静态检查、类型检查或构建通过 | 命令、状态和摘要 |
| `IMP-05` | 回归测试覆盖受影响调用链，未只验证新增正常路径 | 回归范围与结果 |
| `IMP-06` | 安全、数据、迁移或外部依赖专项检查已执行或明确阻塞 | 专项证据 |
| `IMP-07` | 接口、配置、文档和测试与实现保持一致 | 一致性检查 |
| `IMP-08` | diff 中无调试残留、临时数据、密钥或无关变更 | 变更审查记录 |
| `IMP-09` | 报告区分通过、失败、未执行和环境阻塞，结果对应当前状态 | 验证报告 |
| `IMP-10` | 未通过删除测试、降低阈值或缩小范围制造通过 | 门禁与阈值对比 |

## 5. 测试层级

| 层级 | 主要目的 | 典型触发 |
| --- | --- | --- |
| 静态与类型检查 | 发现语法、导入、类型和明显质量问题 | 所有代码变更 |
| 单元测试 | 验证局部规则、纯逻辑、错误分支 | 相关逻辑修改 |
| 集成测试 | 验证组件、数据库、文件系统、API 和事务边界 | 服务或边界修改 |
| 契约测试 | 验证请求、响应、错误码和兼容性 | 公共接口或 Schema 变化 |
| E2E 测试 | 验证完整用户或系统链路 | 主链路和高风险跨模块变化 |
| 质量评测 | 用固定语料或输入和指标验证内容、排序或模型质量 | 质量相关变化与阶段验收 |
| 真实依赖检查 | 验证真实外部环境仍可用 | 显式授权后的独立检查 |
| 全量自动化测试 | 发现跨模块和未知回归 | 命中下方扩大验证条件 |

单元测试不能替代集成测试；测试替身通过不能证明真实外部依赖可用；全量测试通过
也不能替代质量评测、迁移演练、安全检查或人工验收。

## 6. 变更类型与最低验证

| 变更类型 | 默认最低验证 | 扩大条件 |
| --- | --- | --- |
| 纯文档 | 链接、格式、术语和 diff 检查 | 引用接口或配置时同步验证 |
| 独立局部逻辑 | 目标单元测试、静态检查、受影响类型检查 | 成为共享逻辑时增加集成测试 |
| 服务编排 | 单元测试、相关集成测试、静态检查 | 主链路变化增加 E2E |
| 公共 API 或契约 | 契约、API、错误和兼容性测试 | 默认考虑全量测试 |
| 数据库 Schema 或迁移 | 临时数据库集成、约束、升级和回滚验证 | 通常触发全量测试 |
| 核心共享链路 | 定向测试、集成测试和受影响回归 | 默认触发全量测试 |
| 安全、凭据或敏感日志 | 负向测试、泄露检查和安全门禁 | 通常触发全量测试 |
| 质量或模型策略 | 冻结数据评测、基线对比和切片检查 | 阶段验收增加 E2E 和全量测试 |
| 依赖、锁文件、构建或 CI | 干净环境安装、静态检查、构建和测试 | 默认触发全量测试 |
| 无法确定影响面 | 按更高一级风险处理 | 不缩小范围 |

出现多个类别时采用最高验证要求。测试层级选择必须在实现前记录，不得在结果不理想
后倒推减少覆盖。

## 7. 全量测试触发条件

出现任一条件时，应运行全量自动化测试：

1. 数据库 Schema、迁移、事务、级联删除或一致性规则变化。
2. 共享输入处理、解析、状态机、排序、规则决策或模型交互等核心链路变化。
3. 公共 API 契约、跨模块错误码或兼容行为变化。
4. 鉴权、安全边界、敏感日志或密钥处理变化。
5. 依赖、锁文件、运行时版本、测试框架或 CI 配置变化。
6. 大型重构、跨多个模块的重构或无法确定影响范围。
7. 原因不明的跨模块回归。
8. 阶段验收、发布候选或迁移与回滚演练。
9. 用户明确要求全量验证。

本地只运行与变更直接相关的范围，避免重复。CI 可以在每个待合并提交上执行一次
全量门禁；同一状态和同一条件不得反复重跑相同命令。

## 8. 失败处理

- 先分析失败断言、堆栈、输入和环境影响，再决定修复方式。
- 本次修改引入的问题修复后，优先重跑失败测试。
- 影响共享契约时扩大到相关测试集；必要时再运行全量测试。
- 不稳定测试最多重跑一次；仍不稳定时记录名称、频率、环境和可能原因。
- 环境、权限、费用或数据导致无法执行时，必须报告未执行项、替代证据和残余风险。
- 不得把“相关测试通过”写成“全量测试通过”。

## 9. 必须返工的情况

- 实现偏离已批准架构或公共契约，却没有重新设计。
- 快速变更实际改变了契约、数据、安全或共享行为，却没有升级任务模式。
- 验收要求没有验证，或只验证了最容易通过的正常路径。
- 关键失败路径、数据副作用或安全边界未测试。
- 通过删除困难样本、降低门槛或修改生产默认值让测试通过。
- diff 包含无关改动、调试内容、敏感信息或未批准依赖。
- 测试结果来自不同代码状态却用于当前放行。

## 10. 放行规则

- 所有适用阻断项通过：`PASS`。
- 任一适用阻断项失败：`REWORK`。
- 不适用项标记 `N/A` 并说明原因。
- 未运行的必要验证不能以历史结果或推断代替；需要例外时进入 `WAIVER`。
- 门禁证据可以保存在 [`templates/change-record.md`](../templates/change-record.md)、
  测试报告、CI 结果或 commit 中；高风险和 `WAIVER` 场景使用完整评审记录。

## 11. 实现变化与重开

- 发现设计不成立时，停止把实现补丁当作设计修复，回到架构门禁。
- 发现任务范围不可独立验收时，回到任务拆分门禁。
- 变更扩大需求范围时，回到需求门禁。
- 快速变更触及高风险条件时，立即升级模式并补齐受影响的上游分析。
- 实现只调整内部等价方案且不改变契约、数据、风险或验收时，可记录影响分析后继续。
