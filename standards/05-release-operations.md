# 05 发布与运维门禁

门禁编号：`G5`

## 1. 目标

确认交付物可以从当前状态可靠地部署、验证、观测和恢复。对于不涉及部署的变更，
可以在说明理由后对不适用的部分标记 `N/A`，但不能跳过交付有效性检查。

## 2. 适用范围

- `G5` 是发布候选级门禁，只在实际部署、发布、交付或形成需要长期追溯的版本时执行。
- 普通任务完成或本地 commit 不自动触发 `G5`；发布尚未安排时记录
  `NOT_TRIGGERED`，不得写成 `PASS`。
- 发布候选可以包含多个已经通过 `G4` 的快速、标准或高风险任务。
- 只要候选版本包含高风险变更，就必须执行对应安全、迁移、恢复和全量验证。

## 3. 进入条件

- 发布候选中的所有任务均已通过 `G4`，或有明确批准且仍有效的 `WAIVER`。
- 被复用的需求、架构和任务基线仍然有效；高风险变更的受影响上游门禁已经通过。
- 已知缺口、未执行验证和残余风险已记录。
- 发布范围和目标环境明确。

## 4. 阻断标准

| ID | 阻断标准 | 必需证据 |
| --- | --- | --- |
| `REL-01` | 发布候选与已验收产物是同一版本，没有混入未经门禁的变更 | 版本、提交或产物标识 |
| `REL-02` | 安装、部署或启动步骤可由目标环境重复执行 | 发布步骤与试运行记录 |
| `REL-03` | 配置、密钥和环境差异有明确处理，不把密钥写入产物或日志 | 配置清单 |
| `REL-04` | 数据迁移、备份、兼容和恢复条件已验证或明确不适用 | 迁移与恢复证据 |
| `REL-05` | 回滚条件、回滚步骤和回滚后验证明确且可执行 | 回滚方案或演练结果 |
| `REL-06` | 健康检查、关键日志或指标可以发现主要失败 | 运行观测证据 |
| `REL-07` | 发布后有针对主链路的验证步骤和通过标准 | 冒烟或验收记录 |
| `REL-08` | 用户或维护者需要的行为、限制和恢复操作已说明 | 运行或运维文档 |
| `REL-09` | 所有结论对应当前发布候选，不引用历史提交结果冒充当前证据 | 证据索引 |

## 5. 判断说明

- 单机本地工具不一定需要完整发布平台，但至少要有可重复启动、失败识别和恢复方式。
- 数据迁移必须考虑备份、兼容窗口和失败后的数据状态。
- “可以重新部署”不等于“可以回滚”；若重新部署会破坏数据或外部状态，必须定义恢复方式。
- 观测不要求复杂平台；日志、健康检查、退出码或明确的人工检查都可以是有效证据。
- 高风险问题不能只靠发布后观察来替代发布前验证。
- 发布记录必须列出候选版本包含的任务及其 `G4` 结论，避免把任务完成直接当成发布
  验证。

## 6. 必须返工或停止发布的情况

- 发布产物包含未通过上游门禁的变更。
- 迁移或删除操作可能造成不可恢复的数据损失。
- 回滚步骤无法执行，或回滚会留下不一致状态。
- 关键配置或密钥处理不明。
- 发布后无法判断主链路是否正常。
- 用户可见限制没有记录，却把版本标记为完整交付。

## 7. 通过条件与放行规则

- 所有适用阻断项通过：`PASS`。
- 阻断项失败：`REWORK`；不得发布。
- 任一适用检查未执行、环境阻塞或证据缺失：`REWORK`，不得以任务完成或历史发布结果
  替代当前候选版本的证据。
- 不适用项只有在发布范围、环境或交付方式能够证明其确实不适用时，才能标记 `N/A`。
- 因环境或授权无法执行的必要项：进入 `WAIVER`，必须明确依据、影响、风险、恢复
  措施、批准人、适用版本或期限和后续验证；不得把例外写成检查通过。
- 默认在发布说明、部署日志、验证报告或发布记录中保存 `G5` 检查、证据和结论；不
  默认另建评审记录。
- 只有风险审批、审计、独立复核、证据争议、`WAIVER` 或组织流程明确要求时，才使用
  [`templates/gate-review.md`](../templates/gate-review.md)。
- `REL-01` 与 `REL-09` 不得以“后续补证据”方式豁免为完整发布。

## 8. 发布后动作

- 按发布记录执行主链路验证。
- 记录实际结果、版本、时间、环境和异常。
- 出现异常时先执行回滚或恢复判断，再分析根因。
- 将发布后发现转化为新任务或变更记录，不静默扩大当前版本范围。
