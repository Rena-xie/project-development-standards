# 03 任务拆分门禁

门禁编号：`G3`

## 1. 目标

确认任务计划完整、可执行、可验证，并且任务边界不会造成失控依赖、测试滞后或
无法评审的大块变更。任务拆分不以代码行数或固定工期作为主要标准。

## 2. 前置条件

- 架构门禁 `G2` 已 `PASS`，或现有豁免仍然有效且范围明确。
- 已识别项目风险、外部依赖、迁移需求和关键验证方式。

## 3. 输入与产物

输入：

- 已批准需求和验收清单。
- 已通过门禁的架构说明。
- 项目配置中的命令、环境和证据要求。

必需产物：

- 一份基于 [`templates/task-plan.md`](../templates/task-plan.md) 的任务计划。
- 需求到任务、任务到验证的追踪矩阵。
- 任务依赖图或等价依赖清单。
- 一份门禁评审记录。

## 4. 阻断标准

| ID | 阻断标准 | 必需证据 |
| --- | --- | --- |
| `TSK-01` | 每个任务有唯一 ID，并至少承接一条需求、设计约束或明确的使能目标 | 追踪矩阵 |
| `TSK-02` | 一个任务只形成单一、连贯、可描述的完成结果 | 任务目标与范围 |
| `TSK-03` | 任务依赖明确，形成无环图；前置条件可交付 | 依赖图 |
| `TSK-04` | 每个任务都有可独立判断的验收和验证方式 | 验收与证据 |
| `TSK-05` | 测试、迁移、安全、文档和观测工作进入相关任务 | 每任务测试说明 |
| `TSK-06` | 高风险、未知技术或关键外部依赖优先验证 | 风险排序 |
| `TSK-07` | 所有 Must 需求及必要非功能要求都有任务覆盖 | 覆盖矩阵 |
| `TSK-08` | 存在必要的集成检查点，避免长期只完成局部层 | 里程碑与检查点 |
| `TSK-09` | 任务边界允许在一个完整评审单元内理解范围和证据 | 变更影响说明 |
| `TSK-10` | 任务完成后的预期状态可构建、可运行或可验证 | 集成策略 |
| `TSK-11` | 未把范围变化、验收降低或修复未知问题预埋成模糊收尾任务 | 风险与缓冲计划 |

## 5. 任务边界判断

以下情况应拆分：

- 一个任务包含多个相互独立、可分别验收的结果。
- 一个任务同时改变多个高风险边界，无法用一条主验收链路证明。
- 功能、等价重构、数据迁移和发布操作被捆绑在一个任务中。
- 任务过大，评审者无法在一次评审中理解其影响和证据。
- 任务的前半部分完成但后半部分未知，且无法设置中间验收点。
- 同一个任务依赖多个尚未稳定的公共契约。

以下拆分方式通常不合理：

- 仅按“写数据库、写服务、写接口、写界面”横向切分，却没有可独立验证的行为。
- 只写生产代码，把测试、迁移和恢复工作全部留到最后的“大联调”任务。
- 把未知风险留到项目末期的“性能优化”或“问题修复”任务。

基础使能任务可以按技术层拆分，但必须具有明确验收和后续使用路径。

## 6. 必须返工的情况

- 任一 Must 需求没有任务覆盖。
- 任务依赖存在循环，或关键前置任务缺失。
- 任务没有验证方式，只能以“代码写完”判定完成。
- 风险最高且最不确定的工作被安排在末尾。
- 需要多次并行修改同一关键契约却没有同步与集成计划。
- 任务清单依赖尚未批准的架构或产品范围。

## 7. 放行规则

- `TSK-01` 至 `TSK-11` 全部通过：`PASS`。
- 任一阻断项失败：`REWORK`。
- 观察项如难以在实施中高效处理，应明确记录，不得扩为隐性需求。

## 8. 变化与重开

以下变化会使任务门禁失效：

- 架构或公共契约变化。
- 新增、删除或重新定义 Must 需求。
- 关键任务拆分、依赖顺序或验收方式变化。
- 实施中发现需要引入未计划的高风险工作。

重开时先更新任务图和追踪矩阵，再执行门禁。若发现根因属于架构边界问题，应回到
`G2`，不得通过增加更多任务掩盖设计缺口。
