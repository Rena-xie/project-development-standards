# 03 任务拆分门禁

门禁编号：`G3`

## 1. 目标

确认任务计划完整、可执行、可验证，并且任务边界不会造成失控依赖、测试滞后或
无法评审的大块变更。任务拆分不以代码行数或固定工期作为主要标准。

## 2. 适用范围

- 新版本、重要功能或包含多个依赖任务的工作：执行完整 `G3`。
- 已有有效任务基线时：只评审新增、删除或变化的任务和依赖。
- 快速变更且只有一个可独立验证的变更单元：可以直接使用
  任务报告、变更记录或 commit 描述，不另建任务计划。
- 标准开发：建立受影响任务、覆盖关系和必要依赖；多任务或跨模块时再形成完整任务
  计划和追踪矩阵。
- 高风险变更：任务计划还必须覆盖影响分析、验证顺序、迁移、回滚和恢复步骤。

判定深度：

- 新项目、新版本、重大功能、多任务或跨模块工作：建立完整任务清单、依赖图和覆盖矩阵。
- 已有项目的局部变更：只拆分受影响的实现、验证和恢复工作，记录必要依赖。
- 单任务或简单迭代：简短任务说明、现有代码和测试能够证明边界、依赖与验收时，
  不要求新建任务依赖图或完整覆盖矩阵。

## 3. 进入条件

- 本次执行 `G3` 时，架构基线有效，或适用的 `G2` 增量已经 `PASS`。
- 已识别项目风险、外部依赖、迁移需求和关键验证方式。

## 4. 输入与内容标准

输入：

- 已批准或明确复用的需求和验收基线。
- 已通过或明确复用的架构基线，以及本次适用的设计增量。
- 项目配置中的命令、环境和证据要求。

必须满足的内容与判定标准：

- 可以直接引用现有任务计划、Issue、任务报告、commit、PR 描述、测试输出、交付报告
  或其他等价证据，不规定固定文件模板。
- 多任务或跨模块工作必须保留唯一任务 ID、可独立判断的完成结果、依赖关系、需求
  覆盖和验证映射。
- 单任务可以使用任务报告、变更记录或简短任务说明作为计划，直接说明目标、边界、
  依赖和验收证据，不要求依赖图或完整覆盖矩阵。
- 快速单项任务可以把模式、验收、验证和风险直接写入任务说明、任务报告、commit 或
  PR 描述，不生成任务依赖图。
- 标准和高风险的多任务变更保留需求到任务、任务到验证的追踪映射；单任务只记录
  本次影响关系。
- 多任务或跨模块工作时保留任务依赖图或等价依赖清单。
- 任务信息维护任务 ID、任务边界、依赖、覆盖关系和完成定义，但不记录实际结果或
  门禁结论；`G3` 结论可以保存在任务报告、变更记录、commit、PR 描述或项目状态
  记录中，并引用 `TASK`、`CHECKPOINT` ID 和计划版本。
- 只有正式审批、独立评审、审计或其他正式治理流程明确要求时，才建立独立正式记录。

## 5. 阻断标准

| ID | 阻断标准 | 必需证据 |
| --- | --- | --- |
| `TSK-01` | 每个适用任务有唯一 ID，并至少承接一条需求、设计约束或明确的使能目标 | 追踪矩阵、任务 ID 或简短任务说明 |
| `TSK-02` | 一个任务只形成单一、连贯、可描述的完成结果 | 任务目标与范围 |
| `TSK-03` | 任务依赖明确，形成无环图；前置条件可交付 | 依赖图、依赖清单或单任务边界说明 |
| `TSK-04` | 每个任务都有可独立判断的验收和验证方式 | 验收与证据 |
| `TSK-05` | 测试、迁移、安全、文档和观测工作进入相关任务 | 每任务测试说明 |
| `TSK-06` | 高风险、未知技术或关键外部依赖优先验证 | 风险排序 |
| `TSK-07` | 所有适用 Must 需求及必要非功能要求都有任务覆盖 | 覆盖矩阵、受影响映射或单任务说明 |
| `TSK-08` | 存在必要的集成检查点，避免长期只完成局部层 | 检查点或单任务集成边界 |
| `TSK-09` | 任务边界允许在一个完整评审单元内理解范围和证据 | 变更影响说明 |
| `TSK-10` | 任务完成后的预期状态可构建、可运行或可验证 | 集成策略 |
| `TSK-11` | 未把范围变化、验收降低或修复未知问题预埋成模糊收尾任务 | 风险与缓冲计划 |

`TSK-03`、`TSK-08` 和 `TSK-10` 可以在只有一个任务且不产生跨任务集成要求时标记
`N/A`，但必须说明单任务边界。

## 6. 任务边界判断

以下情况应拆分：

- 一个任务包含多个相互独立、可分别验收的结果。
- 一个任务同时改变多个高风险边界，无法用一条主验收链路证明。
- 功能、等价重构、数据迁移和发布操作被捆绑在一个任务中。
- 任务过大，评审者无法在一次评审中理解其影响和证据。
- 任务的前半部分完成但后半部分未知，且无法设置中间验收点。
- 同一个任务依赖多个尚未稳定的公共契约。

以下拆分方式通常不合理：

- 仅按“写数据库、写服务、写接口、写界面”横向切分，却没有可独立验证的行为。
- 只写生产代码，把测试、迁移和恢复工作全部留到最后的“大联调”任务。
- 把未知风险留到项目末期的“性能优化”或“问题修复”任务。

基础使能任务可以按技术层拆分，但必须具有明确验收和后续使用路径。

## 7. 必须返工的情况

- 本次适用范围内的任一 Must 需求没有任务覆盖。
- 任务依赖存在循环，或关键前置任务缺失。
- 任务没有验证方式，只能以“代码写完”判定完成。
- 风险最高且最不确定的工作被安排在末尾。
- 需要多次并行修改同一关键契约却没有同步与集成计划。
- 任务清单依赖尚未批准的架构或产品范围。

## 8. 通过条件与放行规则

- 本次执行 `G3` 时，`TSK-01` 至 `TSK-11` 的适用项通过：`PASS`。
- 任一阻断项失败：`REWORK`。
- 任一适用检查未执行、证据缺失，或证据未对应当前任务计划版本：`REWORK`。
- 观察项如难以在实施中高效处理，应明确记录，不得扩为隐性需求。
- 快速单项任务未执行正式 `G3` 时，在变更记录中记录 `NOT_TRIGGERED`，并由 `G4`
  验证该任务可以独立完成。
- 复用既有任务基线时记录 `REUSED`，不生成新的 `PASS`。
- 简单任务只有简短任务说明、现有代码和测试证据且边界清楚时，可以使用 `REUSED`
  或 `NOT_TRIGGERED`，不要求补建依赖图或覆盖矩阵。

## 9. 变化与重开

以下变化会使任务门禁失效：

- 架构或公共契约变化。
- 新增、删除或重新定义 Must 需求。
- 关键任务拆分、依赖顺序或验收方式变化。
- 实施中发现需要引入未计划的高风险工作。

重开时更新受影响的任务说明、依赖和覆盖映射；只有多任务或复杂变更才要求完整任务图
和追踪矩阵。若发现根因属于架构边界问题，应回到 `G2`，不得通过增加更多任务掩盖
设计缺口。
