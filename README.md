# 项目开发规范包

版本：`0.4.1`

## 1. 定位

本规范包用于跨项目复用阶段门禁，判断某个开发阶段是否已经具备进入下一阶段的
条件。它不定义具体产品需求、项目架构、任务进度或技术栈命令。

规范包采用最小可运行结构：新项目只需要 `AGENTS.md` 和 `standards/`。项目已有需求、
架构、任务或测试载体时直接复用，不要求按照固定模板重写。

可复用规范只回答四个问题：

1. 当前阶段必须满足什么。
2. 产物必须满足哪些可验证标准。
3. 什么情况下必须返工，什么情况下可以记录例外。
4. 如何证明门禁已经执行且结论对应当前产物。

项目自身的 `PROJECT.md`、版本规格、设计文档、任务清单和验证证据仍然属于项目
仓库，本规范包不替代它们。

## 2. 设计原则

- **标准优先，文档从简**：明确阶段要求、通过条件、阻断条件和返工规则。
- **验证必须执行，记录不必冗余**：实际检查代码、测试和证据，不把过程重复抄写到
  额外文件。
- **优先复用现有信息**：已有需求、架构、任务计划和测试结果不重复创建。
- **按任务规模调整流程**：简单任务轻量处理，复杂任务完整评审，高风险任务强化验证。
- **不为形式制造产物**：没有实际维护价值的文档、清单和评审记录不要求生成。

## 3. 门禁层级与任务模式

`G1-G5` 不是每个任务都必须完整重跑的五道流水线：

```text
项目/版本/功能基线：G1 -> G2 -> G3
单个任务：选择任务模式 -> 复用或评审适用基线 -> G4
发布候选：G5
```

门禁层级：

- `G1-G3` 主要是项目、版本或重要功能级基线，也可以按受影响范围做增量评审。
- `G4` 是任务级门禁，每个交付任务执行与风险相称的验证。
- `G5` 是发布候选级门禁，普通任务完成不自动触发。

任务模式：

| 模式 | 典型任务 | 执行策略 |
| --- | --- | --- |
| 快速变更 | 文档、格式、低风险局部 Bug | 复用有效的需求、架构和任务基线，直接执行适用的 `G4`；不自动触发 `G5` |
| 标准开发 | 新功能、跨模块功能 | 按需完成 `G1` 增量，评审受影响 `G2`，拆分 `G3`，执行 `G4` |
| 高风险变更 | 数据迁移、权限、安全、公共契约、共享核心链路 | 重开受影响上游门禁，扩大 `G4`，发布时执行 `G5` |

快速变更不得改变公共契约、数据、权限、安全、依赖或恢复行为。无法确定影响范围时，
升级为高风险变更。三种模式是执行策略，不新增开发阶段。

模式选择先看实际变化和风险，不看任务名称、文件类型或预估工作量。同时命中多个模式
时采用要求最高的模式；任务范围扩大、基线失效或风险被低估时立即升级并重开受影响
门禁。文档修改只有在不改变已批准需求、验收、架构边界或公共契约时才适用快速变更。
完整文档不是快速变更的前置条件，当前行为、现有测试或可复现结果可以作为最小行为
基线；无法确认受影响边界时则必须升级模式。

小型 Bug 的标准路由：

```text
快速变更
  -> G1/G2 = REUSED
  -> G3 = REUSED / NOT_TRIGGERED
  -> G4 = EXECUTED
  -> G5 = NOT_TRIGGERED（未形成发布候选）
```

`G4 PASS` 后任务完成。门禁通过后，只要仍在当前授权范围和已批准设计内，Agent 可以
继续下一项工作或下一阶段，不需要逐阶段等待用户确认。只有重大决策、范围或设计变化、
高风险或不可逆操作、需要额外授权，或用户明确要求确认时才暂停。

## 4. 阶段路由

| 阶段 | 必读规范 | 主要产物 | 通过后 |
| --- | --- | --- | --- |
| 需求确认 | [`standards/01-requirements.md`](standards/01-requirements.md) | 需求与验收基线 | 进入架构设计 |
| 架构设计 | [`standards/02-architecture.md`](standards/02-architecture.md) | 架构、契约、决策与风险 | 进入任务拆分 |
| 任务拆分 | [`standards/03-task-decomposition.md`](standards/03-task-decomposition.md) | 任务、依赖与覆盖矩阵 | 进入实现 |
| 实现与验证 | [`standards/04-implementation-testing.md`](standards/04-implementation-testing.md) | 代码与真实验证结果 | 任务完成；发布时进入 `G5` |
| 发布与运维 | [`standards/05-release-operations.md`](standards/05-release-operations.md) | 发布、回滚与运行验证证据 | 完成交付 |

上表用于建立项目、版本或功能基线。单个任务不按表中顺序强制重走全部门禁，而是按
任务模式复用或增量评审适用基线，然后执行 `G4`。

安全相关变更还必须加载
[`standards/security.md`](standards/security.md)。安全门禁是横切检查，嵌入架构、
实现或发布阶段，不单独增加开发阶段。

## 5. 门禁结论

每个门禁都必须定义进入条件、通过条件、阻断条件和必要证据。缺少其中任一项，或无法
找到证据时，不得判定 `PASS`。

门禁结论只有三种：

- `PASS`：所有适用检查均已执行并满足通过条件，证据对应当前产物版本。
- `REWORK`：任一适用检查失败、未知、未执行、证据缺失或已失效；修正后重新评审。
- `WAIVER`：未满足或无法执行的检查被明确接受。必须记录依据、影响、风险、恢复措施、
  授权人、适用范围或期限和重评条件；它不是检查通过。

规则：

- 阻断项失败默认进入 `REWORK`。
- `REUSED` 和 `NOT_TRIGGERED` 是门禁处置状态，不是新的通过结论。
- 单项检查可以使用 `PASS / FAIL / NOT_RUN / BLOCKED / N/A`，但这些结果不能替代
  门禁结论。
- 非阻断观察项可以记录为后续改进，不影响 `PASS`。
- 安全、数据丢失、公共契约破坏等高危阻断项不得由 Agent 自行豁免。
- 没有执行的检查不能标记为 `PASS`；`N/A` 必须满足不适用条件并说明可验证理由。
- `WAIVER` 没有明确授权、影响说明或恢复条件时仍按 `REWORK` 处理。
- 门禁只对具体产物版本有效。产物发生实质变化后，原结论失效。

默认优先使用已有产物和执行报告记录，不为阶段另建无实际内容的文件：

- 快速变更可以使用任务报告、变更记录、commit 或 PR 描述，不要求另建文件。
- `G1-G3` 将门禁结论写入任务报告、变更记录或无正式评审时的项目状态记录，并引用
  对应需求、架构或任务产物的 ID 和版本。
- `G4` 使用变更记录、测试报告、CI 结果、commit 或任务报告。
- `G5` 使用发布说明、部署日志、验证报告或发布记录。

各阶段只维护一份权威内容：

| 信息 | 唯一权威来源 |
| --- | --- |
| 问题、目标、范围、需求与验收条件 | 项目现有需求文档或版本规格 |
| 组件职责、接口契约、数据所有权、关键流程和技术决策 | 项目现有架构文档、接口规格或决策记录 |
| 任务 ID、任务边界、依赖、覆盖关系和完成定义 | 项目现有任务计划、Issue 或任务报告 |
| 实际测试、CI 和运行结果 | 测试、CI 或运行报告 |
| 正式评审判断、阻断项和豁免 | 按需建立的正式评审记录 |

正式评审记录只引用上述来源的 ID、版本、报告或运行标识，不重复抄写完整内容。没有
正式评审要求时，不创建该记录。

也可以引用已有文档和测试结果，但必须注明版本或标识、位置和仍然有效的理由。同一
门禁只有一个权威结论，不默认再生成独立验收清单或评审记录。只有风险审批、审计、
独立复核、证据争议、`WAIVER` 或组织流程要求正式记录时，才在现有评审系统或
`docs/gates/` 中建立记录。

任务完成、阶段门禁通过和正式发布验收必须分别报告：

- 任务完成：当前任务的 `G4` 通过，或授权 `WAIVER` 明确允许完成。
- 阶段门禁通过：当前阶段产物对指定版本通过，或授权 `WAIVER` 明确允许进入下一阶段。
- 正式发布验收：准确的发布候选版本已执行 `G5` 并 `PASS`，或允许豁免项已获授权。

`G5 = NOT_TRIGGERED` 不是发布通过；`G4 = PASS` 也不能替代发布门禁。

## 6. 评审独立性

- 低风险阶段可以先由产物作者完成自评，并在所选记录载体中明确标注自评或复核方式。
- 架构、安全、数据完整性和发布门禁应由未直接负责该产物的人员或独立评审上下文
  复核；单人环境可以由用户复核高风险结论。
- 无法进行独立复核时，可以继续做技术自评，但不得把自评限制写成“独立评审通过”。

## 7. 在新项目中使用

1. 新建项目根目录。
2. 将本包根目录的 [`AGENTS.md`](AGENTS.md) 和 `standards/` 原样放入新项目根目录，
   不重命名、不嵌套到额外子目录。
3. 不需要替换技术栈、命令、文档路径或规范包路径占位符。工具链从项目清单、脚本和
   CI 中发现；只有确有需要保留的权威内容或证据时才创建默认 `docs/` 文件。
4. 先判断这是建立基线，还是对已有项目执行快速、标准或高风险任务。
5. 只读取任务触及阶段和条件触发规范。
6. 优先在对应主产物、测试结果、任务报告或发布记录中保存门禁证据；只在条件触发时
   建立独立评审记录。
7. 只有适用的上游门禁和 `G4` 为 `PASS`，或存在经批准的 `WAIVER`，任务才能完成。
8. 只有形成发布候选时才执行 `G5`。

规范仓库中的 `README.md`、`VALIDATION.md`、`CHANGELOG.md` 和 `VERSION` 是规范包维护
资料，不需要复制到新项目。新项目只需要 `AGENTS.md` 和 `standards/` 两个直接运行项。

推荐的项目内最小引用方式：

```text
AGENTS.md
  -> 规范包固定版本
  -> 门禁层级与任务模式
  -> 适用规范
  -> 阶段产物或轻量变更记录
  -> 门禁处置与结论
```

规范规则变化时按 [`VALIDATION.md`](VALIDATION.md) 做必要的代表性自测；只有高风险或
影响面较大的结构调整才需要额外样例项目验证。项目不得静默继承未验证的规范变化。

## 9. 当前边界

`0.4.1` 是任务分级、无固定模板版，暂不包含：

- 固定需求、架构、任务、评审和配置模板。
- 产品规格和任务进度管理。
- 特定语言、框架或仓库结构。
- CI 平台实现。
- Codex skill 封装。
- 组织级多人审批和合规流程。

规范包仓库由 Git 管理；新项目直接复制可运行项即可，不需要继承规范仓库的 Git
历史。是否封装为 skill 或增加自动检查脚本，在首个新项目实际使用后决定。
